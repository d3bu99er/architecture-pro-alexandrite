# Задание 1. Анализ, выявление проблем и план действий

## Перечень проблемных зон

Проведите анализ архитектуры и описания системы.

### Текущие проблемы

- **Контроль статусов заказов.** На текущий момент заказ может застревать на одном из этапов. В результате клиент не получает его вовремя и обращается с претензиями в поддержку.

- **Неэффективная организация MES API и MES DB.** Наблюдаются сложности с загрузкой списка заказов на главной странице MES. Точная причина пока не определена.

### Возможные риски

- **Отсутствие налаженного CI/CD.** Деплой в release и production выполняется вручную. На раннем этапе это допустимо, но по мере роста количества релизов увеличиваются затраты и риск ошибок из-за человеческого фактора.

- **Общая база данных (Shop DB).** Одна база используется одновременно CRM API и Shop API. Такой подход иногда оправдан, но чаще рассматривается как анти-паттерн.

## Инициативы

### Инициатива 1: Внедрение контроля жизненного цикла заказов

**Контекст:** Клиенты сообщают, что заказы выполняются месяцами, несмотря на заявленные сроки в несколько недель. При этом производственные ресурсы позволяют обрабатывать заказы даже при увеличении нагрузки.

**Задача:**
- бизнес-команда должна определить допустимое время нахождения заказа в каждом статусе;
- команда разработки — реализовать автоматизированный контроль этих сроков.

> Пример:
> Статус SUBMITTED (заказ оформлен пользователем) должен переходить в статус PRICE_CALCULATED (расчёт стоимости в MES).
>
> Расчёт может занимать до 30 минут (в среднем 2–3 минуты).
>
> Если переход не произошёл в течение 35 минут — необходимо уведомить ответственного.

**Выгода:** Появляется прозрачность процесса и возможность оперативно реагировать на отклонения.

**Реализация:** Предпочтительно реализовать на стороне CRM — например, через отдельный интерфейс с просроченными заказами.

Альтернативный вариант — дашборд в Grafana с алертами. Однако это менее предпочтительно, так как задача носит бизнес-характер.

**Ответственные за реализацию:** команда разработки.

**Ответственные за сопровождение:**
- на старте — продакт-менеджер;
- далее — менеджеры по продажам.

---

### Инициатива 2: Введение технического мониторинга

**Задача:** Помимо бизнес-контроля необходимо внедрить технический мониторинг с алертами по ключевым метрикам.

> Примеры метрик:
> - время ответа API;
> - время обработки сообщений в RabbitMQ;
> - размер очередей RabbitMQ;
> - медленные запросы к БД.

**Выгода:** Проблемы будут выявляться до того, как о них сообщат пользователи.

**Ответственные за реализацию:** команда разработки.

**Ответственные за сопровождение:** команда разработки (с внедрением дежурств).

---

### Инициатива 3: Улучшение производительности MES DB

**Контекст:** Операторы жалуются на медленную загрузку главной страницы MES, где отображается список заказов. Несмотря на добавление фильтров и пагинации, проблема сохраняется.

Критично видеть новые заказы как можно быстрее, поскольку от этого зависит доход операторов.

**Задача:** Найти узкое место и устранить его.

**Выгода:** Ускорение работы интерфейса и повышение эффективности операторов.

**Возможные решения:**
- разделение данных на «горячие» и архивные таблицы;
- оптимизация индексов (например, индекс по статусу «новый»);
- внедрение кеширования.

**Ответственные за реализацию:** команда разработки.

---

### Инициатива 4: Автоматизация CI/CD

**Задача:** Настроить автоматический деплой в release и production окружения.

**Выгода:**
- снижение трудозатрат;
- уменьшение риска ошибок.

**Реализация:** Требуется анализ текущей инфраструктуры. Возможные инструменты — GitLab CI/CD или GitHub Actions.

**Ответственные за реализацию:** команда разработки.

---

### Инициатива 5: Разделение баз данных для сервисов

**Контекст:** CRM API и Shop API используют одну базу данных.

**Задача:** Выделить отдельную БД для каждого сервиса.

**Выгода:**
- устранение единой точки отказа;
- чёткое разделение ответственности.

**Реализация:** Требует дополнительного анализа. Возможно, текущая архитектура допустима — необходимо изучение кода и нагрузочного профиля.

## Вопросы

> Какой вы видите целевую архитектуру через полгода?

**Ответ:**
- внедрён как бизнес-, так и технический мониторинг;
- оптимизирована работа с MES DB.

> Если можно реализовать только три инициативы за полгода — какие выбрать?

**Ответ:** Приоритет следует отдать инициативам 1–3, поскольку они направлены на решение текущих бизнес-проблем, в отличие от инициатив 4–5, которые носят превентивный характер.
